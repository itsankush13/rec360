- **`.github/workflows/ci.yml`** — new. Runs on push/PR to `consolidated`,
  `azure-provider`, `main`. One job: checkout → `setup-python` 3.12 → `pip
  install -r requirements.txt` → `alembic upgrade head` against a throwaway
  sqlite file (catches exactly the two-Alembic-heads incident CLAUDE.md
  records from 2026-09-12, and validates the full migration chain applies
  cleanly from empty, not just the latest revision) → `pytest -q`.
- No `DATABASE_URL` is set for the test step — `tests/conftest.py` already
  builds its own in-memory sqlite engine per test and doesn't read the env
  var, so the app's default (`sqlite:///./tis_app.db`) is never touched by
  CI. `GROQ_API_KEY`/`QUEUE_BACKEND` are set at job level, matching
  `conftest.py`'s own `os.environ` calls, so CI doesn't depend on secrets.

- `.python-version` and `runtime.txt`: `3.11`
- `CLAUDE.md`: "the environment is built and verified on **Python 3.13.5**"
- Actual local venv this session (and every session before it that recorded
  a Python version): **3.12.10** — the only one with an actual passing
  612/612 full-suite run behind it today.

CI is pinned to **3.12** (matching the one empirically green environment),
not 3.11 or 3.13.5. I did not change `.python-version`/`runtime.txt` myself —
those set the deployment target (Render/Heroku-style buildpacks read
`runtime.txt`), which is a decision beyond "make CI reproducible", not just a
file edit. Recommend either fixing `.python-version`/`runtime.txt` to 3.12 to
match reality, or actually installing/verifying 3.13.5 once and updating
CLAUDE.md/CI together — whichever the team intends as the real target. This
has been flagged across multiple session states without a decision; suggest
opening it as a defect (`04-KNOWN-DEFECTS.md`) so it stops being re-flagged
without being tracked.
