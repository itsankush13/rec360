# Identifier model

Backlog: `B20`. Campaign IDs built 2026-09-13 — see below. Candidate/Application/Run IDs
remain unbuilt.

---

## The problem it fixes

Today the phrase "recruitment ID" is used for two different things: the hiring campaign, and
one candidate measured against one campaign. That ambiguity will break email threading,
calendar linking, and the audit trail, because a reply cannot be routed if the ID in the
subject does not identify exactly one application.

---

## The four identifiers

| Identifier | Means | Cardinality |
|---|---|---|
| **Campaign ID** | One role / JD hiring campaign | One per campaign |
| **Candidate ID** | A persistent candidate profile, across campaigns | One per person |
| **Application ID** (also called Recruitment ID) | One candidate CV evaluated against one campaign / JD | One per candidate per campaign |
| **Run ID** | One technical screening execution | Many per campaign |

Read it as: a Candidate can have many Applications. A Campaign has many Applications.
A Run produces or refreshes many Applications.

**Application ID is the one that goes in email subjects and calendar invites.** It is the
only one that identifies a single person in a single hiring process.

## Requirements

- [x] Short and autogenerated, for campaigns: originally a fixed cohort prefix not derived
      from the date (`RC36-01`, `RC36-02`, …, per direct client instruction, 2026-09-12).
      Revised 2026-09-13, again on direct instruction: `RC` + creation date (`YYYYMMDD`) + a
      running number, e.g. `RC20260913-33`. Revised a second time the same day, again on
      direct instruction: the running number replaced with a random number, e.g.
      `RC20260913-58204`, checked against the database and retried on collision (see
      `docs/DECISIONS.md`, all three entries). `Campaign.short_id`, generated in
      `campaign_service._next_short_id`. Candidate / Application / Run IDs still use the
      suggested shapes below, unbuilt. Suggested shapes: `CND-3M8X`, `APP-9R2D`, `RUN-5T1V`.
- [~] Searchable. Stored and shown; no list screen's search box accepts it yet.
- [x] Stored in the database as a column, not derived at render time — for campaigns.
- [ ] Present in: email subjects · calendar events · reports · exports · audit entries ·
      every lifecycle transition row
- [ ] Stop using "recruitment ID" to mean the campaign. Pick one word per concept and use it
      in the UI, the API, the database, and the documents.

## Migration note

The existing tables use 36-character UUIDs (`String(36)`). Do not replace them. Add a short
public identifier alongside the UUID:

- The UUID stays the primary key and the foreign-key target.
- The short ID is a unique indexed column used for display, search, and outbound references.

That keeps the change additive and reversible.

## Open question for the client review

Should the Application ID stay stable if the same candidate is re-screened after a rubric
change? Recommendation: yes, the Application ID stays and a new Run ID is created. The
application is the same hiring conversation; the run is the technical execution.
